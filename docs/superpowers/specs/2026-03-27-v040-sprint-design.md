# v0.4.0 Sprint Design

**Date:** 2026-03-27
**Status:** Approved
**Release:** v0.4.0
**Duration:** 3 days × 2 hours = 6 hours total

## Overview

Feature sprint with quality hardening. Adds multi-agent support, OpenCode agent, agent permissions, auto-sync detection, and "do not edit" banners. Includes render tests and security hardening.

## Version: v0.4.0

SemVer minor — new features (multi-agent config, new agent, permissions), no breaking changes. Old `agent:` format supported with deprecation warning. Schema version stays `"0.1"` — the new fields are additive and optional.

## Schedule

| Day | Tasks | ~Time |
|-----|-------|-------|
| Day 1 (Mon) | "Do not edit" banner + OpenCode agent + Multi-agent config/parsing/template | 2h |
| Day 2 (Tue) | Multi-agent rendering/sync + Agent permissions + Auto-sync check | 2h |
| Day 3 (Wed) | Render tests + Security hardening + Release v0.4.0 | 2h |

Dependencies drive the order: banner is independent; OpenCode is needed before multi-agent testing; multi-agent must precede permissions; quality goes last when features are stable.

**Rollback plan:** Each feature can ship independently. If multi-agent is incomplete by Day 2, ship banner + OpenCode + quality as v0.3.2 and defer multi-agent + permissions to the next sprint.

## Day 1 (Monday): Banner + OpenCode + Multi-agent config

### 1. "Do not edit" banner in generated files (20 min)

**Problem:** Users manually edit generated files, then lose changes on `isolde sync`.

**Solution:** Add a banner to every file generated by `isolde sync`:

| File | Banner format |
|------|--------------|
| `.devcontainer/Dockerfile` | `# ⚠ Auto-generated by Isolde. Do not edit. Run 'isolde sync' to regenerate.` |
| `.claude/CLAUDE.md` | `<!-- ⚠ Auto-generated by Isolde. Do not edit. Run 'isolde sync' to regenerate. -->` |
| `.devcontainer/devcontainer.json` | `"_comment": "Auto-generated by Isolde. Do not edit. Run 'isolde sync' to regenerate."` field in root JSON object |
| `.claude/settings.json` (new, Day 4) | `"_comment": "..."` field |
| `opencode.json` (new, Day 4) | `"_comment": "..."` field |

**Not affected:**
- `.devcontainer/features/*` — copied as-is from `core/features/`, not generated
- `isolde.yaml` — user-owned file

**Files to modify:**
- `isolde-core/src/devcontainer.rs` — `render_devcontainer_json()`, `render_dockerfile()`, `render_claude_md()`
- Update existing render tests (~5 tests) to expect the banner

### 2. OpenCode agent support (1h)

**Problem:** Only Claude Code and Codex are implemented as agents. OpenCode (anomalyco/opencode) is a popular open-source alternative.

**Solution:** Add OpenCode as a fully supported agent, following the same pattern as Codex.

**New files:**
- `core/features/opencode/devcontainer-feature.json` — feature metadata
- `core/features/opencode/install.sh` — installation via `curl -fsSL https://opencode.ai/install | bash`
- `templates/opencode/template-info.yaml` — template metadata
- `templates/opencode/.devcontainer/devcontainer.json` — devcontainer template
- `templates/opencode/.devcontainer/Dockerfile` — Dockerfile template

**Installation:** `curl -fsSL https://opencode.ai/install | bash` with version pinning via `VERSION` env var.

**Note:** Verify `https://opencode.ai/install` URL is accessible before implementation. If the URL is unstable, fall back to `npm i -g opencode-ai@latest` as alternative install method.

**Proxy:** OpenCode respects standard `HTTP_PROXY`/`HTTPS_PROXY` env vars. The existing `proxy` feature sets these, so no special proxy integration is needed.

**Node.js:** OpenCode is TypeScript-based. Like claude-code and codex, it needs Node.js. The `devcontainer.json.tera` template should include a node feature. The deduplication logic in `render_devcontainer_json()` already handles this via `matches!(config.agent_name(), "claude-code" | "codex")` — extend to include `"opencode"`.

**Config:** `opencode.json` in project root for settings (generated only when permissions are configured — see Day 4).

**Changes to existing files:**
- `isolde-cli/src/commands/init.rs` — add `opencode` to `is_agent_implemented()`
- `isolde-core/src/config/v0_1/mod.rs` — add `opencode` to agent name validation in `AgentConfig::validate()`
- `isolde-core/src/devcontainer.rs` — extend Node.js check: `matches!(name, "claude-code" | "codex" | "opencode")`
- `presets.yaml` — optionally add an opencode preset

### Multi-agent config schema + parsing + template refactor (Day 1 continued)

### 3. Multi-agent per container — config and templates (1.5h)

**Problem:** Current config supports only a single `agent:` block. Users want multiple agents in one devcontainer (e.g., Claude Code for design + Codex for implementation).

**New config format (`isolde.yaml`):**
```yaml
version: "0.1"
name: my-project
docker:
  image: ubuntu:latest
agents:
  - name: claude-code
    version: latest
    options:
      models:
        fast: claude-sonnet-4-20250514
  - name: opencode
    version: latest
```

**Backward compatibility (soft migration):**
```yaml
# Old format — works but prints deprecation warning
agent:
  name: claude-code
  version: latest
```

#### 3a. Config parsing (`isolde-core/src/config/v0_1/mod.rs`)

- Add `agents: Option<Vec<AgentConfig>>` field (serde optional)
- Change `agent` field to `Option<AgentConfig>` with `#[serde(default)]`
- Validation rules (in `validate()` method):
  1. Neither `agent` nor `agents` present → default to `agents: vec![default_agent_config()]` (preserves backward compat for minimal configs like `test_config_deserialize_minimal`)
  2. Both `agent` and `agents` present → error: "Use `agents:` list format. `agent:` is deprecated."
  3. `agent:` only → convert to `agents: vec![agent]` + print deprecation warning to stderr
  4. `agents:` only → use as-is
  5. Each agent name must be unique in the list
  6. Each agent must pass `AgentConfig::validate()` (the existing validation with `validate_chars()`)

**Important:** The conversion from `agent:` to `agents:` should happen in a normalization step after deserialization but before validation, so that the rest of the codebase only deals with `agents: Vec<AgentConfig>` (never `Option`).

#### 3b. Config API (`isolde-core/src/config.rs`)

- New: `config.agents() -> Vec<AgentConfigView>` — returns all agents
- Existing single-agent methods kept **without** `#[deprecated]` attribute (to avoid flooding CI with warnings). Add a code comment `// DEPRECATED: use agents() instead` for developer guidance:
  - `config.agent_name()` → returns first agent's name
  - `config.agent_version()` → returns first agent's version
  - `config.agent_options()` → returns first agent's options
  - `config.agent_option_str()` → returns first agent's option
- New: `AgentConfigView` struct with `name()`, `version()`, `options()`, `option_str()`, `permissions()`

#### 3c. Template refactor (`isolde-core/src/template.rs`)

The current `TemplateContext` struct has singular placeholders (`{{agent_feature_path}}`, `{{agent_options_json}}`). These `.tera` templates need updating for multi-agent:

**Approach:** Replace singular agent placeholders with a loop-friendly structure:
- `{{agent_feature_path}}` → `{{agents_features_json}}` — JSON object of all agent features
- `{{agent_options_json}}` → folded into `{{agents_features_json}}`
- `{{plugin_manager_block}}` — stays as-is (only activates if any agent is claude-code with plugins)

Update `TemplateContext::new()` and `build_context()` in `template.rs` to accept `&[AgentConfigView]` instead of single agent fields.

Update template files in `templates/*/` directories to use new placeholders. Note: template files are plain JSON (`templates/*/.devcontainer/devcontainer.json`), not `.tera` files. The Tera engine processes them at rendering time regardless of extension.

#### 3d. Tests

- Parse multi-agent YAML
- Parse single `agent:` with deprecation path
- Parse minimal config (no agent at all) → defaults to claude-code
- Reject `agent:` + `agents:` together
- Reject duplicate agent names
- Validate agent names in list

## Day 2 (Tuesday): Multi-agent rendering/sync + Permissions + Auto-sync

### 4. Multi-agent — generator, sync, and rendering (1.5h)

#### 4a. Rendering (`isolde-core/src/devcontainer.rs`)

**`render_devcontainer_json()`:**
- Loop over `config.agents()` to build features object
- Each agent gets `"./features/{name}": { agent options }` entry
- **Node.js deduplication:** Collect all agents' dependency requirements. If any agent is in `["claude-code", "codex", "opencode"]`, add the node feature once (not per agent).
- **Plugin-manager:** Activates if *any* agent is `claude-code` and `config.plugins()` is non-empty. This preserves current behavior — plugins are claude-code-exclusive.

**`render_claude_md()`:**
- Update `"- **Agent**: {}"` to list all agents: `"- **Agents**: claude-code, opencode"` (or singular `"- **Agent**: claude-code"` if only one).

**`render_dockerfile()`:**
- No changes needed — agents are installed via features, not Dockerfile.

**`expected_artifacts()`:**
- Already dynamic — change to iterate `config.agents()` for feature directories.

#### 4b. Generator (`isolde-core/src/generator.rs`)

- `copy_core_features()` already copies ALL feature directories from `core/features/` unconditionally — no changes needed for the copy step
- Update `is_agent_implemented()` guard to validate all agents in the list before proceeding
- Use updated `TemplateContext` from Day 2 (pass all agents)

#### 4c. Sync (`isolde-cli/src/commands/sync.rs`)

- Same as generator: `copy_core_features()` already copies all features
- Update agent guard check to validate all configured agents
- Pass all agents to template rendering

#### 4d. Other callers to update

Full audit of single-agent API usage (12+ call sites across 5 files):

| File | Current usage | Action |
|------|--------------|--------|
| `devcontainer.rs` (~7 calls) | `config.agent_name()`, `config.agent_options()` | Migrate to `config.agents()` loop |
| `template.rs` (~4 calls) | `config.agent_name()` in `build_context()` | Already refactored in Day 2 (3c) |
| `sync.rs` (~1 call) | `config.agent_name()` for feature copy | Migrate to loop |
| `generator.rs` (~2 calls) | `config.agent_name()` for feature copy | Migrate to loop |
| `init.rs` (~1 call) | agent selection in wizard | Keep single-select for v0.4.0 (see note) |
| `validate.rs` (~1 call) | `config.agent_name()` for display | Migrate to `config.agents()` |

**Note on `mounts.rs`:** Currently does not reference `agent_name` at all (verified by grep). No changes needed — agents don't require per-agent mount directories.

**Note on interactive wizard (`init.rs`):** Multi-agent selection in the interactive wizard is **deferred to a future sprint**. For v0.4.0, the wizard continues to select a single agent. Multi-agent is configured by manually editing `isolde.yaml`. This avoids a non-trivial UX change (multi-select checkboxes) that is outside the scope of this sprint.

#### 4e. Feature install order

When multiple agents are present, features install in this order:
1. `proxy` (if configured) — sets env vars needed by agent installers
2. Agent features in order of appearance in `agents:` list
3. `plugin-manager` (if any claude-code agent has plugins)

This matches the current single-agent order extended to N agents.

#### 4f. Error handling

If one agent feature directory doesn't exist (e.g., `gemini` is not implemented), the whole sync fails with an error listing the missing agent. This is consistent with the existing `is_agent_implemented()` guard.

#### 4g. Tests

- Generate project with 2 agents — verify both feature dirs exist
- Sync with 2 agents — verify devcontainer.json has both features
- `expected_artifacts` with multi-agent config
- `render_claude_md` lists all agents
- Node.js feature appears once even with 2 Node-dependent agents

### Agent permissions + auto-sync check (Day 2 continued)

### 5. Agent permissions preset (45 min)

**Problem:** New devcontainer projects require manual agent permission setup. Users want to pre-configure permissions in `isolde.yaml`.

**Config format:**
```yaml
agents:
  - name: claude-code
    version: latest
    permissions:
      allowed_tools: ["bash", "edit", "read", "write"]
      allowed_commands: ["npm test", "cargo build", "make"]
      deny_commands: ["rm -rf /"]
```

**Permissions struct (`isolde-core/src/config/v0_1/mod.rs`):**
```rust
#[derive(Debug, Clone, Deserialize, Serialize, Default)]
pub struct AgentPermissions {
    #[serde(default)]
    pub allowed_tools: Vec<String>,
    #[serde(default)]
    pub allowed_commands: Vec<String>,
    #[serde(default)]
    pub deny_commands: Vec<String>,
}
```

Add `permissions: Option<AgentPermissions>` to `AgentConfig`.

**Mapping to native agent formats:**

| Isolde permission | Claude Code (`settings.json`) | Codex | OpenCode (`opencode.json`) |
|---|---|---|---|
| `allowed_tools` | `allowedTools` | not supported (warn) | `tools` |
| `allowed_commands` | `allowedCommands` | `--approval-mode` (partial) | `permission` (partial) |
| `deny_commands` | `denyCommands` | not supported (warn) | not supported (warn) |

**Generation (`isolde-core/src/devcontainer.rs`):**
- New `render_agent_settings(agent: &AgentConfigView) -> Option<(String, String)>` function
  - Returns `Some((path, content))` for agents with permissions, `None` otherwise
  - For Claude Code: generates `.claude/settings.json` with mapped fields
  - For Codex: limited mapping, unsupported fields → warning to stderr
  - For OpenCode: generates `opencode.json` in project root
- All generated settings files include "do not edit" banner (`"_comment"` field)

**Sync (`isolde-cli/src/commands/sync.rs`):**
- After generating devcontainer files, loop over agents and call `render_agent_settings()` for each
- Write settings files to project root

**`expected_artifacts()`:**
- Add `.claude/settings.json` if any claude-code agent has permissions
- Add `opencode.json` if any opencode agent has permissions

**Validation:**
- If user sets a permission that the agent does not support → warning at `isolde sync` time (not error)
- `permissions` section is optional — if absent, agent runs with its defaults

**Files to modify:**
- `isolde-core/src/config/v0_1/mod.rs` — `AgentPermissions` struct, add to `AgentConfig`
- `isolde-core/src/devcontainer.rs` — `render_agent_settings()`, update `expected_artifacts()`
- `isolde-cli/src/commands/sync.rs` — call settings generation

### 6. Auto-sync on config change (45 min)

**Problem:** Users edit `isolde.yaml` and forget to run `isolde sync`, then `isolde build`/`run` uses stale config.

**Mechanism:** Compare mtime of `isolde.yaml` vs `.devcontainer/devcontainer.json` before build/run.

**Logic:**
1. `devcontainer.json` does not exist → warning: "Run `isolde sync` first"
2. `isolde.yaml` mtime > `devcontainer.json` mtime → warning:
   ```
   ⚠ isolde.yaml has been modified since last sync. Run `isolde sync` to update.
   ```
3. mtimes in order → continue silently

**Implementation:**
- New module `isolde-core/src/sync_check.rs` with `check_sync_freshness(cwd: &Path) -> Option<SyncWarning>`
- `SyncWarning` enum: `NeverSynced`, `ConfigNewer`
- Called in `commands/build.rs` and `commands/run.rs` before execution
- Warning only, does **not block** execution — user decides

**Files to modify:**
- `isolde-core/src/sync_check.rs` — new module
- `isolde-core/src/lib.rs` — add `pub mod sync_check;`
- `isolde-cli/src/commands/build.rs` — call `check_sync_freshness()` before build
- `isolde-cli/src/commands/run.rs` — call `check_sync_freshness()` before run

**Tests:**
- Newer config → returns `ConfigNewer`
- Missing devcontainer.json → returns `NeverSynced`
- Fresh config → returns `None`

### 8. Security hardening (30 min)

**8a. `curl | bash` integrity in install.sh scripts:**
- For `claude-code/install.sh`: verify npm package integrity (npm does this natively)
- For `opencode/install.sh`: the official install script handles verification; add `set -euo pipefail` and validate downloaded binary exists before execution
- For `codex/install.sh`: npm handles integrity natively

**8b. Shell injection in `su -c` and variable usage:**
- Audit all `install.sh` files in `core/features/`
- Quote all variable expansions: `"$VERSION"`, `"$USERNAME"`
- Use `--` to terminate option parsing where applicable
- Replace `su -c "command $VAR"` with safer alternatives where found

**8c. `source` state file validation:**
- In feature scripts that `source` files: check file exists and is a regular file before sourcing
- Add guard: `[ -f "$file" ] && source "$file"` pattern

**Files to audit:**
- `core/features/claude-code/install.sh`
- `core/features/codex/install.sh`
- `core/features/opencode/install.sh` (new)
- `core/features/proxy/install.sh`
- `core/features/plugin-manager/install.sh`
